Capture new durable conventions, invariants, and recurring pitfalls here when they will help future agents make better decisions.

- Use implicit return types instead of explicit annotations
- Prefer `const` arrow functions over `function` declarations
- Assignment capacity counts non-reverted `PENDING` and `APPROVED` logs. Complete, resubmit, and recurrence/status edits must validate and write in one transaction; SQLite's deferred transactions need a write lock before reading capacity. Resubmission retains the original `createdAt` cadence window.
- Assignment cadence uses household calendar boundaries, not time since completion. Display ranges must not truncate the completion history used for eligibility; "Completed last cycle" means the immediately preceding calendar cycle met its target.
- New assigned tasks require shared presets; existing personal-preset assignments remain valid. Inline task creation (`assignedTasks.createWithPreset`) writes the shared preset and its assignment in one transaction so a failed assignment leaves no orphan preset; reuse `src/lib/presetInput.ts` schemas rather than redefining preset fields. Assignees and task creators are nullable, and completion points and approval defaults belong to the completer. Broadcast completion pushes only after commit.
- Check generated SQLite migrations for unrelated table rebuilds (Prisma may include `PresetTaskOrder`); keep shared-board migrations scoped to `AssignedTask` and preserve existing task-log links.
- After making changes, run `pnpm check` (i18n + lint + compile + build + test)
- Playwright e2e (`pnpm test:e2e`, `e2e/`) is outside `pnpm check` and Jest. Keep it to a few core flows. Playwright starts the web server before global setup, so the server command recreates and migrates the throwaway DB; global setup only seeds accounts. Each test seeds its own household so retries stay isolated. Sign in once per account through `storageState`, because the login limiter allows about 10 attempts per IP. Never wait for `networkidle`, since the SSE stream keeps the network busy. Open dashboards with `openDashboard` and Tasks with `openTasks`, which waits for the stream request as a sign of hydration; clicks made before hydration are lost. Set `E2E_SKIP_BUILD=1` to reuse an existing build.
- If Jest warns about a haste naming collision with `.next/standalone/package.json`, it is caused by an existing build artifact; the tests still run, but the warning can be removed by cleaning `.next/standalone`
- Keep `HOSTNAME=0.0.0.0` in the Docker image: Next.js standalone uses Docker's container hostname otherwise, leaving the loopback health check unreachable. Startup smoke tests should exercise the image's default bind address.
- Docker liveness uses `/api/health`, which bypasses the proxy and has no auth or database dependencies. Keep the Dockerfile healthcheck and startup smoke probe aligned with this route.
- Keep CI's Node version aligned with the pinned Docker base. Startup uses Node/Prisma directly; package managers are intentionally absent from the final image.
- On WSL, `docker.exe` can reach Docker Desktop without WSL integration. A `git archive HEAD` build context includes only committed changes.
- Keep dependency audits and image scans informational, including scanner/reporting failures. Ordinary PR Docker builds use the cache; release builds refresh the base and report both architectures of the exact published digest, including on retries. Assess actual exposure from full reports rather than blocking on advisory presence; see README's security checks.
- Releases are managed by Release Please in `.github/workflows/ci.yml`. Use Conventional Commit titles; `feat`, `fix`, and `perf` trigger releases. Do not manually bump versions, create tags, or publish images. Tags retain the `x.y.z` format without a `v` prefix. Only a successful CI run for the merged release PR can publish its image; rerun that workflow to recover a failed publication.
- `cancel-in-progress: false` still replaces pending runs in a shared concurrency group unless `queue: max` is set. Keep main CI grouped by commit and release/publication jobs queued and serialized so release commits are processed and the `latest` check/write cannot race.

- Reward caps are additive rules: shared household, each member separately, and named-member rules all apply together, with no overrides. Keep allowance checks and point deductions in the same transaction. Calendar periods use the household timezone (weeks start Monday); rolling windows use elapsed minutes and exclude claims exactly at the expired boundary. Only approved, non-reverted reward logs consume allowance.
- Household settings saves must send only edited fields. Keep skipped background responses available until the draft becomes clean, and seed the query cache from successful saves before accepting further refreshes.

- Monthly reward accounting uses append-only effective-month policy versions, immutable grant month/amount, forfeited unused units, and per-claim allocations. Never recalculate past grants from current rule columns; those columns describe requested settings, which may start next month. First carryover enablement only changes the current grant's carry treatment, never its amount or historical usage.
- Monthly availability must exclude grants whose startsAt is in the future and select the current grant from started grants, even after a server clock rewind. Persisted accounting is not a historical snapshot; do not undo recorded forfeitures or allocation state when the clock moves backwards.
- Advance monthly accounts before releasing a reward allocation, in the same transaction as the log reversal. Released allocation timestamps preserve past-boundary usage; historical claims without allocations get no extra refund. Non-carrying grants expire at their boundary, while saved grants have null expiry. Keep existing banks above a reduced cap; only newly banked units are capped/forfeited.
- Rule saves reconcile IDs with a household rewardClaimRevision; unversioned legacy payloads may echo unchanged rules, but cannot remove/replace them. Omitted rolloverEnabled preserves the stored value. Scope/target/period changes retire the old identity; active rule queries must filter archivedAt: null. Membership IDs identify individual accounts so rejoining cannot accrue through gaps or inherit the former account.
- SQLite rollover migrations must be additive and preserve the existing RewardClaimLimit CHECK constraints. Initialize only the known current month on upgrade; retain over-limit historical allocations as debt. Account/rule and grant/month unique keys plus transactional creation prevent restart/retry grants. Query-only Prisma extensions preserve the generated transaction API; casts at accounting call sites bridge Prisma's incompatible extension delegate types.

- Dashboard board visibility is `role !== "DOER" || hasActiveAssignedTasks || householdDoneThisWeek > 0`: approvers see it even in empty households; raw ACTIVE assignments keep it visible even when all current periods are fulfilled. Its household done count uses the household calendar-week start and includes pending completions; the personal weekly summary retains its rolling seven-day window.
- The Tasks hub lives at `/[householdId]/tasks` with `tab=todo` (default, omitted from links) and `tab=done`, plus approver-only `tab=manage`. Resolve DOER Manage requests to To do before management data loads. Manage lists all ACTIVE tasks, including ones fulfilled this cycle, uses full qualifying history for progress, ignores range params, and hides member/range controls; tab links still preserve them. `/assignments` redirects approvers to Manage and DOERs to To do. `/week` redirects with all query params, selecting Done when any range param is present. To do shares the dashboard's `buildAssignedTaskEntries` derivation and full-history loader, independent of display ranges. Member selection resolves a current member or `all` from the query, then the existing `tskr-week-member-${householdId}` cookie, then Everyone. Every range/member/tab URL carries `userId`. A member's To do includes their assigned tasks plus Open tasks; Done contains completions only and filters by completer, including quick logs (`assignedTaskId: null`). Eligibility still uses everyone's full task history. `calendarWeek` is the default Done range; legacy range keys keep their trailing-window meaning.
- Radix `Select` inside a form keeps a hidden native `<select>` in sync; if a controlled value and its newly added `SelectItem` arrive in the same render, it fires `onValueChange("")`. Ignore empty values in handlers when items are added on the fly (see `AssignTaskCard`).

- UI vocabulary: use task, Open (no assignee), and Quick log (one-tap logging that does not count towards listed tasks). Avoid chore, assignment, and preset in UI copy; internal names may keep them.
